# 실전에서 활용 가능한 퀀트 투자 에이전트를 구현하기 위한 설계

> 본 문서는 [퀀트 투자 에이전트 아키텍처 설계안](./퀀트%20투자%20에이전트%20아키텍처%20설계안.md)이 제시한 개념(Multi-Agent, Deterministic-First, Risk Kill-Switch)을 **이 저장소의 실제 코드베이스**에 맞춰 지금 바로 구현 가능한 형태로 재설계한 것이다. 원안은 LangGraph/CrewAI/Backtrader/PostgreSQL 같은 새 스택 도입을 전제로 하지만, 이 프로젝트는 이미 [agent_architecture.md](./agent_architecture.md)가 정의한 **Gemini(google-genai) 기반 7-에이전트 토론 시스템**을 목표로 `src/data/krx_provider.py`, `src/data/gsheet_provider.py`를 구축해 둔 상태다. 따라서 새 퀀트 엔진은 경쟁하는 별도 시스템이 아니라, **시황 분석 에이전트(Market Analyst)의 결정론적 백엔드**로 통합하는 것을 전제로 한다.

---

## 1. 이론적 퀀트 투자 에이전트 아키텍처 (원안 요약)

실전 재해석에 들어가기 전에, [퀀트 투자 에이전트 아키텍처 설계안](./퀀트%20투자%20에이전트%20아키텍처%20설계안.md)이 제시한 이론적 설계를 먼저 정리한다. 이 설계는 "단일 스크립트 매매 프로그램"에서 "역할 기반 다중 에이전트 시스템"으로의 패러다임 전환을 전제로 하며, 아래 네 층위로 구성된다.

### 1.1 멀티 에이전트 아키텍처

```
                  ┌────────────────────────┐
                  │   Orchestrator Agent   │
                  │ (전체 파이프라인 제어)  │
                  └───────────┬────────────┘
                              │
  ┌─────────────────┬─────────┴─────────┬─────────────────┐
  ▼                 ▼                   ▼                 ▼
[Data Collector]  [Strategy Agent]    [Risk Manager]   [Executor Agent]
(가격/재무/수급/  (팩터 스코어링/    (MDD/Stop-Loss/  (API 주문 집행/
 뉴스 수집)        신호 생성)          포지션 사이징)   슬리피지 통제)
```

| 에이전트 | 역할 | 핵심 로직 |
|---|---|---|
| **Data Collector** | 시장 데이터(OHLCV, 수급, 팩터) 및 비정형 데이터(뉴스, 공시, 13F 등) 수집 | Open DART, KRX API, Naver/Yahoo Finance API, Web Scraper |
| **Strategy Agent** | 수집 데이터 기반 정량적 알파 신호 생성 | 멀티 팩터(Value+Quality+Momentum) 결합, 기술적 지표(볼린저밴드/이동평균) 산출 |
| **Risk Manager** ★가장 중요 | 전략 에이전트의 매수/매도 제안을 위험 통제 규칙으로 검증·수정 | MDD 제한, Trailing Stop-Loss 판정, 변동성 타겟팅 기반 포지션 사이징 |
| **Executor Agent** | 최종 승인 주문을 증권사 API로 실제 집행 | 분할 주문(VWAP/TWAP), 미체결 재조정, 슬리피지 관리 |

이를 프로덕션 수준으로 보강하면 각 노드가 내부에 세부 서브 에이전트를 갖는 구조로 확장된다.

```
                                  [ Orchestrator / Supervisor Node ]
                                                 │
      ┌───────────────────────────┬──────────────┴──────────────┬───────────────────────────┐
      ▼                           ▼                             ▼                           ▼
[ Data Collector ]       [ Signal Engine ]              [ Risk Engine ]            [ Execution & Ops ]
  - Market Data            - Technical Factor             - Trailing Stop            - Order Router
  - Major Flow             - Flow Filter                  - Portfolio MDD            - Sheet/Dashboard
  - Macro/Earning          - Cross-Validation             - Circuit Breaker          - Alert Service
```

### 1.2 아키텍처 설계 원칙

1. **Stateful Graph 기반 샌드박스화(Isolation)**: 데이터·신호산출·리스크·주문의 각 기능 단위를 독립된 Sub-graph/Node로 격리해 상태(State) 오염을 방지한다.
2. **Deterministic-First, LLM-Second (결정론 우선 법칙)**: 백테스팅, 이동평균/볼린저밴드 계산, 수급 조건 판정, Trailing Stop-Loss 등 모든 수치적 판단은 Python 코드로만 집행한다. LLM은 (1) 뉴스/공시의 정성적 리스크 감지, (2) 매매 근거 자연어 요약, (3) 예외 상황 시 Supervisor 인터럽트 처리에만 제한적으로 사용한다.
3. **Pydantic Strict Response Schema**: 에이전트 간 주고받는 모든 메시지·데이터 객체를 Pydantic 기반 Strict JSON Schema로 검증해 타입 불일치로 인한 오작동을 원천 차단한다.

### 1.3 추천 기술 스택 (원안)

| 구분 | 추천 기술 | 용도 |
|---|---|---|
| Agent Framework | LangGraph, CrewAI | 순환(Loop)·상태(State) 관리가 필수인 금융 에이전트에 적합 |
| Data Processing | Pandas, NumPy, Polars | 전처리, 팩터 계산, 수정주가 처리 |
| Backtesting | Backtrader, PyAlgoTrade, 자체 Engine | 파라미터 최적화 및 Out-of-sample 검증 |
| Data Source | Open DART API, 한국투자증권 API, FinanceDataReader | 국장/해외 주가지수, 재무제표, 수급 데이터 |
| Storage & Dashboard | PostgreSQL / Google Sheets(GAS) | 거래 기록, 포트폴리오 상태, 실시간 모니터링 |

### 1.4 리스크 통제 레이어 (Fail-safe)

에이전트가 오작동해도 계좌 파산을 막는 **하드코딩된 리스크 룰**이 최우선 적용되어야 한다는 것이 원안의 핵심 안전장치다. 예: 자산 대비 일일 최대 손실률 -2% 초과 시 전체 주문 강제 취소 및 전량 현금화(Kill-Switch). 세부 엔진 설계는 다음과 같다.

- **Trailing Stop-Loss Engine**: 보유 종목의 포지션 오픈 이후 최고가(High Water Mark) 대비 -N% 하락 시 LLM 추론 없이 즉시 `FORCE_SELL` 신호 발생
- **Portfolio MDD & Volatility Target Engine**: 일별/월별 포트폴리오 MDD가 임계치(예 -5%)에 도달하면 즉시 Kill-Switch 작동, 신규 매수 전면 동결
- **LLM Qualitative Risk Analyzer(선택)**: 횡령·배임·감사의견 관련 악재 공시/뉴스를 텍스트 파싱해 Risk Level(Low/Medium/High) 부여, High면 매수 거부

### 1.5 AgentState 데이터 스키마 (원안)

```python
class StockMetrics(BaseModel):
    ticker: str
    stock_name: str
    close_price: float
    ma_20: float
    bollinger_upper: float
    volume_ratio: float
    net_institution_buy: float   # 투신 + 연기금 순매수
    net_foreigner_buy: float

class SignalOutput(BaseModel):
    ticker: str
    signal_score: float          # 0~100 팩터 결합 점수
    action: str                  # BUY, SELL, HOLD
    target_weight: float
    signal_reasons: List[str]

class RiskCheckResult(BaseModel):
    ticker: str
    is_approved: bool
    trailing_stop_price: float
    mdd_status: str
    risk_notes: Optional[str] = None

class QuantSystemState(BaseModel):
    market_phase: str             # PRE_MARKET, REGULAR, POST_MARKET
    collected_stocks: Dict[str, StockMetrics] = {}
    generated_signals: List[SignalOutput] = []
    approved_signals: List[SignalOutput] = []
    portfolio_mdd: float = 0.0
    kill_switch_activated: bool = False
```

### 1.6 원안의 단계별 로드맵

| Phase | 내용 |
|---|---|
| 1. 코어 매매 파이프라인 단일 스크립트 구축 (1~2주) | 데이터 수집→팩터 계산→가상 주문 생성 기본 파이프라인, 수수료/슬리피지 반영 백테스트 연결 |
| 2. LangGraph 기반 Multi-Agent 상태망 구현 (2~3주) | Data→Strategy→Risk→Execution Node 그래프 구축, AgentState 스키마 설계, Risk Node에 Trailing Stop·변동성 타겟팅·수급 필터링 탑재 |
| 3. 모니터링 및 대시보드 연동 (1~2주) | 구글 시트/Streamlit 대시보드, 텔레그램/슬랙 알림 봇 연동 |
| 4. 모의투자를 통한 실전 검증 (2~4주) | 증권사 모의투자 API 연동, 룩어헤드 편향·슬리피지 영향 최종 체크 후 실전 투입 |

이 이론적 설계는 **"무엇을 만들어야 하는가"에 대한 완결된 청사진**을 제공하지만, 어떤 스택을 언제 도입할지에 대한 판단은 프로젝트마다 다르다. 아래 2장부터는 이 청사진을 이 저장소의 실제 코드베이스·의존성·진행 상황에 맞춰 "지금 무엇부터 만들 수 있는가"의 관점으로 재구성한다.

## 2. 원안 대비 실전 구현 관점의 재해석

| 원안(퀀트 에이전트 아키텍처 설계안)의 제안 | 실전 적용 판단 | 사유 |
|---|---|---|
| LangGraph/CrewAI 기반 상태 그래프 | **보류 (Phase 3 이후 선택)** | 현재 `requirements.txt`에 없고, 7-에이전트 토론 흐름은 이미 `orchestrator.py`(agent_architecture.md 4장)로 설계돼 있어 별도 그래프 프레임워크 없이 함수 호출 체인으로도 충분히 구현 가능 |
| Backtrader/PyAlgoTrade | **보류 (선택적 확장)** | 팩터 수 개 수준의 벡터화 백테스트는 pandas만으로 충분히 빠르고 디버깅이 쉬움. 다전략 이벤트 기반 백테스트가 실제로 필요해지는 시점에 재검토 |
| PostgreSQL | **보류** | 이미 구글 스프레드시트를 상태 저장소로 쓰는 설계(`gsheet_provider.py`)가 있고, 분석 이력은 로컬 JSON(`.history/`, agent_architecture.md 7.4)으로 충분 |
| Pydantic Strict Schema | **채택** | 유일하게 즉시 추가할 가치가 있는 의존성. LLM 출력과 결정론적 신호를 분리하는 원안의 핵심 안전장치를 아주 저비용으로 구현 가능 |
| Deterministic-First, LLM-Second | **채택 (그대로)** | 원안에서 가장 중요한 원칙. 아래 전체 설계의 근간으로 유지 |
| Trailing Stop / MDD Kill-Switch | **채택 (그대로)** | agent_architecture.md 7.1의 위기 레벨(주의/경고/긴급) 및 8.3의 손절 기준(-15%)과 **동일한 규칙 체계로 통합** — 두 문서가 서로 다른 손절 기준을 갖지 않도록 일원화 |

**결론**: 원안의 "정신"(결정론과 LLM의 분리, 실패 안전장치)은 100% 채택하되, "수단"(LangGraph, Backtrader, Postgres)은 지금 당장 필요하지 않다. 최소 의존성으로 Phase 1~2를 먼저 동작시키고, 실제로 병목이 확인된 지점에서만 무거운 프레임워크를 도입한다.

## 3. 통합 아키텍처

```
src/
├── data/                         # (기존) 외부 데이터 연동 — 그대로 재사용
│   ├── krx_provider.py           #  get_krx_listings(), get_stock_price()
│   ├── gsheet_provider.py        #  get_portfolio_from_gsheet()
│   └── flow_provider.py          #  ★신규: 외국인/기관/(투신+연기금) 수급 수집
│
├── quant/                        # ★신규: 결정론적 퀀트 엔진 (LLM 미개입 영역)

│   ├── schema.py                 #  Pydantic 기반 State/Signal/RiskResult 정의

│   ├── risk_engine.py            #  Trailing Stop / MDD / Kill-Switch 판정
│   └── backtest.py               #  벡터화 백테스트 (수수료/슬리피지 반영)
│
├── agents/                       # (agent_architecture.md 4장에서 이미 계획된 구조)
│   ├── base_agent.py
│   ├── market_agent.py           #  ★quant 엔진 호출 지점 — 아래 5장 참고
│   └── ...(macro/screener/company/supply/news/risk)
│
└── orchestrator.py                #  7-에이전트 토론 중재 (agent_architecture.md 2~7장)
```

**핵심 통합 지점**: `market_agent.py`는 LLM에게 "수급이 어떤지 판단해줘"라고 묻지 않는다. 대신 `quant/signal_engine.py`와 `quant/risk_engine.py`가 산출한 **숫자와 판정 결과**를 프롬프트에 주입하고, LLM(Gemini)은 그 숫자를 근거로 한 **자연어 해석과 보고서 작성**만 담당한다. 이것이 원안 3장의 "결정론과 비결정론의 분리" 원칙을 이 프로젝트의 실제 에이전트 구조에 적용하는 방식이다.

## 4. 데이터 스키마 (`src/quant/schema.py`)

원안의 `QuantSystemState`를 이 프로젝트의 실제 데이터 소스(6자리 종목코드, 원화 금액 단위)에 맞게 축소·조정했다.

```python
from pydantic import BaseModel, Field
from typing import List, Dict, Optional, Literal
from datetime import datetime

class StockMetrics(BaseModel):
    ticker: str = Field(description="종목코드 6자리")
    stock_name: str
    close_price: float
    ma_20: float
    ma_60: float
    bollinger_pct_b: float          # %B: 0=하단, 1=상단
    volume_ratio: float             # 전일 대비 거래량 비율
    net_foreigner_buy: float        # 원 단위, 외국인 순매수
    net_institution_core_buy: float # 원 단위, (투신+연기금) 순매수 — '금융투자' 단기자금은 제외

class SignalOutput(BaseModel):
    ticker: str
    signal_score: float = Field(ge=0, le=100)
    action: Literal["BUY", "SELL", "HOLD"]
    target_weight: float = Field(ge=0, le=1)
    signal_reasons: List[str]

class RiskCheckResult(BaseModel):
    ticker: str
    is_approved: bool
    trailing_stop_price: float
    crisis_level: Literal["normal", "caution", "warning", "emergency"]
    risk_notes: Optional[str] = None

class QuantRunState(BaseModel):
    timestamp: str = Field(default_factory=lambda: datetime.now().isoformat())
    mode: Literal["realtime", "batch"]
    collected_stocks: Dict[str, StockMetrics] = {}
    generated_signals: List[SignalOutput] = []
    approved_signals: List[SignalOutput] = []
    portfolio_mdd: float = 0.0
    kill_switch_activated: bool = False
```

`crisis_level`의 값과 임계치는 **agent_architecture.md 7.1과 완전히 동일한 정의**를 사용한다(VIX≥25/35/50, 손절 -15% 등). 두 시스템이 서로 다른 위기 판정 기준을 갖는 것을 방지하기 위해, 실제 구현에서는 이 임계치를 `src/quant/risk_engine.py`가 아니라 `src/config/risk_policy.py`처럼 **한 곳에서만 정의**하고 양쪽 문서/코드가 참조하도록 한다.

## 5. 핵심 모듈 설계

### 5.1 `factors.py` — 결정론적 팩터 계산 (순수 함수, LLM 미개입)

```python
def calc_moving_average(df: pd.DataFrame, window: int) -> pd.Series: ...
def calc_bollinger_pct_b(df: pd.DataFrame, window: int = 20, num_std: float = 2.0) -> pd.Series: ...
def calc_volume_ratio(df: pd.DataFrame) -> pd.Series: ...
```

기존 `krx_provider.get_stock_price()`가 반환하는 DataFrame(Open/High/Low/Close/Volume)을 그대로 입력받도록 설계해, 데이터 계층을 새로 만들 필요가 없다.

### 5.2 `flow_provider.py` — 수급 데이터 신규 수집 (`src/data/` 확장)

현재 `src/data/`에는 가격 데이터(krx_provider)와 사용자 포트폴리오(gsheet_provider)만 있고, **외국인/기관 수급 데이터 소스가 없다.** 이는 원안 2장 Data Collector의 "Flow Data Collector"에 해당하며, 실전 퀀트 엔진의 전제조건이므로 최우선으로 채워야 하는 공백이다.

- 1차 후보: `FinanceDataReader`가 제공하지 않는 투자자별 매매동향은 KRX 정보데이터시스템(data.krx.co.kr) 공개 API 또는 증권사 API 연동 필요
- 이번에 실행한 [intraday-supply-demand 워크플로우](../.agent/workflows/intraday-supply-demand.md)처럼 웹 조회로 대체하는 방식은 **일회성 리포트에는 적합하지만, 매일 자동 실행되는 배치 파이프라인에는 부적합**(속도·안정성·구조화 실패). 배치용 `flow_provider.py`는 반드시 구조화된 API/파일 응답을 반환하는 소스로 구현해야 한다.

### 5.3 `signal_engine.py` — 신호 생성

원안 3장 ②의 조건 A/B 앙상블 로직을 그대로 채택:

```python
def generate_signal(metrics: StockMetrics) -> SignalOutput:
    tech_score = _technical_score(metrics)   # 조건 A: 20일선 상단 + %B 상단 돌파 + 거래량 150%↑
    flow_score = _flow_score(metrics)        # 조건 B: 최근 3일 중 2일 이상 외국인/핵심기관 동시 순매수
    combined = 0.5 * tech_score + 0.5 * flow_score
    action = "BUY" if combined >= 70 else ("SELL" if combined <= 30 else "HOLD")
    return SignalOutput(ticker=metrics.ticker, signal_score=combined, action=action,
                         target_weight=_weight_from_score(combined),
                         signal_reasons=_explain(tech_score, flow_score))
```

`signal_reasons`는 자연어가 아니라 **구조화된 근거 코드**(예: `"MA20_BREAKOUT"`, `"FLOW_CO_BUY_2D"`)로 반환한다. 이 근거 코드를 자연스러운 한국어 문장으로 풀어 쓰는 것이 시황 에이전트(LLM)의 역할이다 — 원안의 "LLM은 요약에 한정" 원칙을 실제 함수 인터페이스 수준에서 강제하는 방법이다.

### 5.4 `risk_engine.py` — 실패 안전장치 (★ 가장 먼저 만들어야 할 모듈)

```python
def check_trailing_stop(entry_high_water_mark: float, current_price: float, stop_pct: float = 0.15) -> bool:
    """agent_architecture.md 8.3의 -15% 손절 기준과 동일 규칙."""
    return (entry_high_water_mark - current_price) / entry_high_water_mark >= stop_pct

def evaluate_crisis_level(vix: float, credit_spread_bp: float, yield_curve_bp: float) -> str:
    """agent_architecture.md 7.1 표와 완전히 동일한 임계치."""
    if vix >= 50 or credit_spread_bp >= 300 or yield_curve_bp <= -50:
        return "emergency"
    if vix >= 35:
        return "warning"
    if vix >= 25 or yield_curve_bp < 0:
        return "caution"
    return "normal"

def apply_kill_switch(state: QuantRunState, portfolio_mdd: float, mdd_limit: float = -0.05) -> QuantRunState:
    if portfolio_mdd <= mdd_limit:
        state.kill_switch_activated = True
        state.approved_signals = [s for s in state.generated_signals if s.action == "SELL"]
    return state
```

이 모듈은 **LLM 호출이 전혀 없는 순수 Python 함수**로만 구성한다. `emergency` 판정이나 손절 조건은 시황 에이전트의 "의견"이 아니라 코드가 강제하는 사실이어야 하며, 이는 원안 3장 ③ Fail-safe Mechanisms의 핵심 취지다.

### 5.5 `backtest.py` — 벡터화 백테스트

Backtrader 없이 pandas 벡터 연산만으로 signal_engine/risk_engine과 **동일한 함수**를 과거 데이터에 그대로 통과시킨다. "실전과 동일한 로직으로 검증한다"는 원안 5장의 취지를 프레임워크 도입 없이 달성하는 방법이며, 함수를 공유하기 때문에 실전 로직과 백테스트 로직이 divergence(괴리)될 위험이 원천적으로 없다.

## 6. `market_agent.py` 통합 예시 (결정론 → LLM 순서 강제)

```python
def run_market_agent(ticker: str) -> str:
    price_df = krx_provider.get_stock_price(ticker, start_date=...)
    flow_df = flow_provider.get_investor_flow(ticker, days=5)          # 4.2에서 신규 구현
    metrics = build_stock_metrics(ticker, price_df, flow_df)           # factors.py 조합

    signal = signal_engine.generate_signal(metrics)                    # 결정론 (LLM 미개입)
    risk = risk_engine.check_and_approve(signal, portfolio_state)       # 결정론 (LLM 미개입)

    if not risk.is_approved:
        return f"[리스크 차단] {ticker}: {risk.risk_notes}"            # LLM 호출 자체를 생략

    # 여기서부터만 LLM 사용 — 숫자 해석과 보고서 문장 생성
    prompt = build_market_report_prompt(metrics, signal, risk)
    return gemini_client.generate(prompt)
```

리스크 엔진이 승인하지 않은 신호는 **LLM에게 도달하지도 않는다.** 이는 "LLM이 오작동해도 계좌 파산을 막는 하드코딩 규칙이 최우선"이라는 원안 3장 ③을 인터페이스 레벨에서 물리적으로 강제하는 설계다.

## 8. 결론 — 무엇을 지금 당장 만들 수 있는가

1. **오늘 시작 가능한 것**: Phase 0~2(결정론적 팩터·신호·리스크 엔진)는 신규 외부 의존성이 사실상 없고(`pydantic` 하나), 기존 `krx_provider.py`만으로 동작한다. LangGraph/Backtrader 도입 여부와 무관하게 즉시 착수 가능.
2. **가장 먼저 풀어야 할 문제**: 수급 데이터 파이프라인(`flow_provider.py`) 부재. 이 저장소의 다른 워크플로우들(`intraday-supply-demand`, `weekly-institutional-flow`)이 매번 웹 조회로 수급을 확보하는 것도 같은 공백의 방증이며, 이 공백을 구조화된 API로 메우는 것이 "리포트 생성"에서 "자동 매매 파이프라인"으로 넘어가기 위한 전제조건이다.
3. **당장 도입하지 않아도 되는 것**: LangGraph, CrewAI, Backtrader, PostgreSQL. 에이전트 수가 늘어나 상태 그래프의 순환/분기가 복잡해지거나, 다전략 이벤트 기반 백테스트가 실제로 필요해지는 시점에 재검토한다.
4. **두 설계 문서의 정합성 유지**: 리스크 임계치(VIX, 손절률, MDD)는 `agent_architecture.md`와 본 문서가 서로 다른 숫자를 갖지 않도록 `src/config/risk_policy.py` 단일 소스로 관리한다.
